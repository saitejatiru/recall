<task type="checkpoint:human-action" gate="blocking">
  <name>Checkpoint: Run bake-off, record winning model, test failover</name>
  <what-built>
    bakeoff.html is a standalone page with three pre-filled sample answers and a model
    selector. This checkpoint runs the bake-off with real NIM keys to confirm the AI
    responds correctly, selects the primary model, and tests key rotation by using an
    invalid first key.
  </what-built>
  <read_first>
    - .planning/phases/01-proxy-hosting/01-RESEARCH.md — read the "Bake-Off / Scoring sheet"
      section and "Failover Testing / Method 1" section before starting
    - docs/SETUP.md Sections 7 and 8 (first visit + bake-off)
  </read_first>
  <how-to-verify>
    PART A — Bake-off across models:

    Step 1 — Open https://saitejatiru.github.io/recall/bakeoff.html
    (or open bakeoff.html directly from the repo in your browser — either works).
    Worker URL and passcode should be pre-filled from config.js and localStorage.

    Step 2 — Select model: `nvidia/nemotron-3-super-120b-a12b` (Primary).
    Click "Run bake-off". Wait 15–30 seconds.
    Record results for all three answers: JSON valid? Score for each? Fix quality? Latency?

    Step 3 — Select model: `nvidia/nemotron-3.5-lightning-30b-a3b` (Speed / Fallback).
    Click "Run bake-off". Wait. Record results.

    Step 4 — Evaluate against RESEARCH.md scoring sheet:
      Answer 1 (vague): expect score 2–4
      Answer 2 (strong): expect score 7–9
      Answer 3 (rambling): expect score 2–4
      A model is TOO LENIENT if Answer 1 or 3 scores >= 6.
      A model is TOO HARSH if Answer 2 scores < 6.
      A good "fix" is PM-specific (not generic "add more detail").
      Latency target: < 3 seconds per answer.

    Step 5 — Choose the model that scores most accurately and meets the latency target.
    In Cloudflare Dashboard → Worker `recall-proxy` → Settings → Variables:
    Edit `PRIMARY_MODEL` to the winning model ID → Save and Deploy.

    PART B — Failover test (confirms key rotation works):

    Step 6 — In Cloudflare Dashboard → Worker Settings → Secrets:
    Edit `NIM_KEY_1` → paste any invalid string (e.g. a random 20-character string) → Save.
    DO NOT click Deploy yet — save only.

    Step 7 — Click Deploy (or the Worker auto-deploys on secret save — check if it did).

    Step 8 — Run bakeoff.html again with the same model.
    Expected: results still arrive (Worker rotated to NIM_KEY_2). Latency may be slightly
    higher. If results fail, the rotation loop has a bug — do not proceed, describe the error.

    Step 9 — RESTORE NIM_KEY_1: Edit `NIM_KEY_1` back to your real first API key → Save → Deploy.

    Step 10 — Run bakeoff.html one final time to confirm everything is back to normal.
  </how-to-verify>
  <resume-signal>Type "bakeoff-done" and note the winning model ID and the failover test result (passed/failed), or describe issues.</resume-signal>
  <acceptance_criteria>
    - Bake-off returns valid JSON (score, went_right, fix, rewrite, tags) for all three answers
    - Chosen model scores Answer 1 and 3 in range 2–4 and Answer 2 in range 7–9
    - PRIMARY_MODEL Worker variable updated to the winning model ID
    - Failover test: results still returned when NIM_KEY_1 is invalid (NIM_KEY_2 picks up)
    - NIM_KEY_1 restored to real value after failover test
  </acceptance_criteria>
  <done>
    Primary model is confirmed by bake-off with real keys. Failover rotation is verified.
    Worker is back to full configuration with all valid keys.
  </done>

<task type="checkpoint:human-verify" gate="blocking">
  <name>Checkpoint: Final end-to-end verification — no secrets in repo, no keys in browser</name>
  <what-built>
    All Phase 1 work is complete. This checkpoint verifies the security guarantees:
    no keys in git history, no keys visible in browser network traffic, auth rejection
    working from wrong origin and missing passcode.
  </what-built>
  <how-to-verify>
    Run ALL of the following checks. Every check must pass.

    CHECK 1 — Git history clean (automated, run in repo root Git Bash / WSL):
      git log -p --all | grep -E "nvapi-[A-Za-z0-9_-]{40,}"
    Expected: NO output. If anything appears, Phase 1 cannot be sealed until the secret
    is removed from git history (use `git filter-repo` or contact GitHub support).

    CHECK 2 — Working tree clean (automated):
      grep -rE "nvapi-[A-Za-z0-9_-]{40,}" . --include="*.js" --include="*.html" --include="*.json" --include="*.md"
    Expected: NO output.

    CHECK 3 — Auth rejection, no passcode (automated, replace WORKER_URL):
      curl -s -o /dev/null -w "%{http_code}" -X POST WORKER_URL \
        -H "Origin: https://saitejatiru.github.io" \
        -H "Content-Type: application/json" \
        -d '{"task":"ping"}'
    Expected: 403

    CHECK 4 — Auth rejection, wrong origin (automated):
      curl -s -o /dev/null -w "%{http_code}" -X POST WORKER_URL \
        -H "Origin: https://evil.example.com" \
        -H "Content-Type: application/json" \
        -d '{"task":"ping","passcode":"YOUR_PASSCODE"}'
    Expected: 403

    CHECK 5 — Successful ping with correct credentials (automated):
      curl -s -X POST WORKER_URL \
        -H "Origin: https://saitejatiru.github.io" \
        -H "Content-Type: application/json" \
        -d '{"task":"ping","passcode":"YOUR_PASSCODE"}'
    Expected: {"ok":true,"ts":...}

    CHECK 6 — No Authorization header visible in browser (manual):
    Open https://saitejatiru.github.io/recall/ in Chrome → DevTools (F12) → Network tab.
    Watch the Worker POST request that fires on page load (the ping call).
    Click on the request → Headers tab.
    Confirm: NO "Authorization" header visible in the Request Headers section.
    The Worker adds Authorization internally; it must NOT appear in the browser request.
    (This is expected to pass by design — the browser sends only Content-Type; the Worker
    adds Authorization server-side when calling NIM.)

    CHECK 7 — AI status visible in app (manual):
    https://saitejatiru.github.io/recall/ shows "AI: Connected" in the header.
    If your passcode is not set in this browser session, enter it in the setup modal first.

    CHECK 8 — Incorrect passcode triggers Offline (manual):
    Open DevTools → Application → Local Storage → https://saitejatiru.github.io.
    Change the `passcode` value to anything wrong → hard-refresh page.
    AI status should show "AI: Offline" (not "Connected").
    Restore the correct passcode value → hard-refresh → "AI: Connected" returns.
  </how-to-verify>
  <resume-signal>Type "verified" when all 8 checks pass, or list which checks failed with the output you saw.</resume-signal>
  <acceptance_criteria>
    - CHECK 1: `git log -p --all | grep -E "nvapi-[A-Za-z0-9_-]{40,}"` → NO output

  </acceptance_criteria>
